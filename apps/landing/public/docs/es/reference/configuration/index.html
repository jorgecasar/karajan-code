fallback: la cadena que corre cuando la primera opción no puede

Sección titulada «fallback: la cadena que corre cuando la primera opción no puede»

Cualquier rol acepta un fallback, y un fallback acepta el suyo, así que la cadena es tan larga como necesites (cinco eslabones; a partir de ahí kj avisa e ignora el resto):

Campo Tipo Default Descripción
provider string — El agente de este eslabón. Obligatorio.
model string | null null El modelo de este eslabón. null pide el default del proveedor.
max_wait_hours number 12 Ante un muro de cuota, esperar en vez de cambiar cuando el enfriamiento sea menor que esto. Un modelo retirado no espera nunca: no hay nada que lo devuelva.
fallback object ninguno El eslabón siguiente. La misma forma, recursiva.

Dos cosas que conviene saber porque no se ven:

  • La cadena se recorre en el orden que escribiste, y el modelo por defecto del proveedor se añade como último eslabón cuando (y solo cuando) fijaste un modelo. Ese paso ocurría antes en silencio dentro de cada agente, y por delante de lo que hubieras declarado; desde la 4.33.0 es la cola de tu cadena, donde se ve.
  • Un eslabón que repite al primario se salta, y también uno cuyo proveedor no existe, avisando de cuál. Reintentar el mismo proveedor y el mismo modelo no es avanzar, solo lo parece.

Agotada la cadena, el error dice qué se probó y en qué orden, y kj recuerda un modelo que vio retirar a un proveedor para que la siguiente ejecución no vuelva a pagar esa llamada muerta. Nunca te toca el pin: te nombra la línea para que la cambies tú.

Nota

coder_options.fallback_coder y reviewer_options.fallback_reviewer son la forma antigua: un solo paso y solo de proveedor. Siguen funcionando. roles.<role>.fallback es la que cubre todos los roles y puede cambiar el modelo.

budget

Sección titulada «budget»

Nota

Costes estimados, no facturación real. Karajan ejecuta agentes CLI (Claude Code, Codex, etc.) bajo tus suscripciones existentes — no tiene coste adicional. El sistema de budget cuenta tokens y estima lo que la sesión habría costado si usaras las APIs directamente, basándose en las tarifas publicadas. Es útil para comparar enfoques y establecer guardarraíles, no para facturación.

Campo Tipo Default Descripción
warn_threshold_pct number 80 Avisar cuando el gasto estimado alcance este % de max_budget_usd
currency enum usd Moneda de visualización: usd o eur
exchange_rate_eur number 0.92 Tipo de cambio EUR a USD
pricing object Built-in Tarifas de pricing por agente para estimación (input_per_million, output_per_million)

La sección pricing también puede definirse en el fichero .karajan.yml a nivel de proyecto para sobrescribir tarifas de estimación por proyecto.

release_check

Sección titulada «release_check»

Lo que kj release check comprueba además de los genéricos (manifest contra CHANGELOG contra tags, escaneo de privacidad de los ficheros publicables, la policy vigente). Cada item lo pone el proyecto.

Campo Tipo Descripción
name string Con qué nombre se informa del item
command string Se pasa a sh -c; exit 0 es pasar. {version} se sustituye por la versión del manifest
file_contains.path string Fichero a leer, relativo al proyecto
file_contains.pattern string Texto que tiene que aparecer; {version} se sustituye también
remedied_by string El comando que REPARA este item, si lo hay

remedied_by existe porque un item en rojo no puede bloquear justo la acción que lo pondría en verde. El caso es la landing: el check quiere el sitio desplegado con la versión nueva, y el despliegue que lo consigue estaba bloqueado por ese mismo check. Las palabras tienen que aparecer en el comando en orden, así que firebase deploy cubre firebase --account a@b --project p deploy --only hosting:main.

El item levantado sigue en rojo en el informe, porque el hecho no ha cambiado, y el gate dice cuál ha levantado. Lo demás sigue bloqueando, y publicar el paquete no se exime nunca: npm publish y gh release create son irreversibles, diga lo que diga un item.

Perfiles de modo de revisión

Sección titulada «Perfiles de modo de revisión»

El ajuste review_mode controla la exigencia del reviewer al evaluar código:

standard (por defecto)

Sección titulada «standard (por defecto)»
  • Prioridad: Seguridad → Corrección → Tests → Arquitectura → Estilo
  • Bloquean: Problemas de seguridad, errores lógicos, tests rotos, sobreescritura de ficheros
  • No bloquean: Sugerencias de estilo

paranoid

Sección titulada «paranoid»
  • Filosofía: Todo cambio es sospechoso hasta que se demuestre seguro
  • Prioridad: Seguridad → Corrección → Tests → Integridad de datos → Arquitectura → Estilo
  • Bloquean: Todas las comprobaciones de seguridad, falta de manejo de errores, falta de validación de inputs, falta de tests, sobreescritura de ficheros
  • Umbral de confianza: Aprobar solo si confianza > 0.85. Default a RECHAZO

strict

Sección titulada «strict»
  • Prioridad: Seguridad → Corrección → Tests → Arquitectura → Estilo
  • Bloquean: Todos los problemas de seguridad, errores lógicos, cobertura de tests insuficiente, falta de manejo de errores para llamadas externas
  • Umbral de confianza: Rechazar si confianza < 0.80

relaxed

Sección titulada «relaxed»
  • Filosofía: Preferir aprobar con sugerencias
  • Prioridad: Seguridad crítica → Bugs claros → Tests de rutas críticas
  • Bloquean: Solo seguridad crítica (secrets, SQL injection, XSS) y errores lógicos claros
  • Umbral de confianza: Rechazar si confianza < 0.60

custom

Sección titulada «custom»

Usa el fichero base reviewer.md (a nivel de proyecto, global o built-in) sin un perfil predefinido. Control total a través de tu fichero review-rules.md.

Jerarquía de resolución de ficheros

Sección titulada «Jerarquía de resolución de ficheros»

Las instrucciones de rol se resuelven en este orden (el primero encontrado gana):

  1. Proyecto: <proyecto>/.karajan/roles/{rol}.md
  2. Global: ~/.karajan/roles/{rol}.md
  3. Built-in: templates/roles/{rol}.md (incluido con Karajan)

Los perfiles de modo de revisión siguen el mismo patrón:

  1. .karajan/roles/reviewer-{modo}.md
  2. ~/.karajan/roles/reviewer-{modo}.md
  3. templates/roles/reviewer-{modo}.md

Los plugins se cargan de todas las ubicaciones (no first-wins):

  1. <proyecto>/.karajan/plugins/*.js
  2. ~/.karajan/plugins/*.js
